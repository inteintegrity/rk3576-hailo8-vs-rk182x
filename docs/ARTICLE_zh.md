# RK3576 三种加速器的单路与多路推理实测（YOLO26n）

RK3576 自带 6 TOPS 的 NPU，主板上还有一个 M.2 插槽可以插外部加速模块。我们把**同一个
YOLO26n** 分别放到三种加速器上跑——片内 NPU、RK182x 模块、Hailo-8 模块，
单路与多路各测一轮，看它们的适用场景差别在哪。

## 三种架构，三种并行方式

| 加速器 | 并行方式 | 本次使用的推理接口 |
|---|---|---|
| RK3576 内置 NPU | 2 个 NPU 核，一路一核 | rknn-toolkit-lite2，每次调用一帧 |
| RK182x（M.2） | 8 个 NPU 核，一路一核 | rknn3lite，每次调用一帧 |
| Hailo-8（M.2） | 单设备、无用户可见核划分；靠设备内部流水线 | `InferModel` 的 `run_async`，常驻 4–8 个推理在飞 |

测法因此不同：前两者**一路独占一核**，Hailo-8 则是**N 路汇聚进一个设备**。
但报的是同一个指标——**同时服务 N 路时的总吞吐（aggregate FPS）**。
要求 Hailo 按"一核一路"工作本身就是错的比较方式。

## 测量条件

- 模型：`yolo26n`，COCO 80 类，640×640，INT8。三端图边界一致（六个 one2one 原始检测头），
  解码与 NMS 由**同一份主机代码**执行（`common/postprocess_common.py` +
  `common/postprocess_yolo26.py`），输入逐字节一致（三份记录里的测试视频 sha256 相同）。
- Hailo 用**官方预编译 HEF**，走 Hailo 文档给出的吞吐路径（`create_infer_model()` →
  `configure()` → `run_async()`，常驻 4 个推理在飞；这也是 `hailortcli run` 内部的做法）；
  RK182x 用**官方量化配方**（w8a8 + score 分支 w16a16）；RK3576 用同样的图边界自行转换
  （rknn-toolkit2 2.3.2）。
- 视频：3840×2160 原片（394 帧）。本机没有硬件解码器，4K 软解要 60.7 ms/帧，
  因此从同一段视频派生 640×640 版本用于加速器对比（解码仅 2.1 ms/帧）。
- 多路测试为"每路独立解码视频 + 独立推理"，**不含画框与视频编码**（那是主机 CPU 的活）。

## 单路：Hailo-8 领先

![单路推理](../results/figures/single_stream_bars.png)

| 加速器 | 仅推理 | + letterbox/解码/NMS | + 画框与写视频 |
|---|---:|---:|---:|
| Hailo-8（4 个推理在飞） | **51.2 FPS** | **49.2 FPS** | 28.3 FPS |
| RK3576 内置 NPU | 32.9 FPS | 23.5 FPS | 15.1 FPS |
| RK182x | 22.8 FPS | 17.5 FPS | 13.1 FPS |

394 帧整片，同一套流程。"仅推理"与"端到端"两列口径一致；中间一列（`pipeline_without_io`）在
两端含义不同：Hailo-8 含读帧与 letterbox，RK 两端不含（这两项另记在
`read_letterbox_infer_decode`，同口径换算为 RK3576 21.7 FPS、RK182x 15.9 FPS）。
**Hailo-8 的管道吞吐是内置 NPU 的 2.1 倍**：
它的设备服务速率 51.2 FPS 已达到 Hailo 官方 CLI 实测 52.5 FPS 的 97%，
而设备单帧延迟只有 13.9 ms（另两端约 30 ms、44 ms）。
"仅推理"一栏都是各 runner 自己对加速器调用的实测：Hailo-8 是设备在管线满负荷下的服务速率，
RK 两端是 394 帧一次调用的平均耗时换算。

## 多路：Hailo-8 服务到满速但不增长

![多路聚合吞吐](../results/figures/multi_stream_scaling.png)

| 并发路数 | Hailo-8（单设备） | RK3576 内置 NPU（2 核） | RK182x（8 核） | RK182x/NPU |
|---:|---:|---:|---:|---:|
| 1 路 | 50.3 | **21.2** | 16.2 | 0.76× |
| 2 路 | 51.3 | **43.2** | 34.4 | 0.80× |
| 4 路 | 51.6 | 52.3 | 57.0 | 1.09× |
| **8 路** | 51.6 | 69.7 | **88.6** | **1.27×** |

- **Hailo-8 的总量是平的**：接 1 路还是 8 路都是 50–52 FPS，每路只能分到 1/N（8 路时每路
  6.5 FPS）。这次"平"的位置就是**设备自身的上限**——8 路 + 仅设备口径（不做主机解码）实测
  52.2 FPS。它是一台**固定吞吐设备**：设备独占打开（连 Hailo 官方 CLI 开第二个进程都被拒），
  不向用户暴露核划分，也不随路数增长；要加吞吐就得**加模块**。
- **RK3576 内置 NPU 并非"核数封顶"**：SoC 上是 2 个 NPU 核，1–2 路时一路独占一核效率最高
  （21 → 43 FPS）；4/8 路时多路共享这 2 个核，聚合继续上涨（52 → 70 FPS），
  8 路时已经**超过 Hailo-8**（69.7 对 51.6）。
- **RK182x 增长到 88.6 FPS**（8 核），是 Hailo-8 的 1.7 倍，但只比内置 NPU 高 **1.27 倍**——
  早期版本把它的"8 路"和 NPU 的"3 路"并列，得出 1.8 倍，是取样档位不齐导致的，现已补齐
  （原 1/2/3 路记录仍在 `results/multi_stream/rk3576_multi_stream_1to3_runs.json`）。

## 结论

| 场景 | 选择 | 依据 |
|---|---|---|
| 单路 / 单相机 | **Hailo-8** | 49.2 vs 23.5 FPS（内置 NPU），单帧延迟 13.9 ms 最低，且不占 SoC 的 NPU |
| 单路但不想插模块 | 内置 NPU | 23.5 FPS，免费、无模块、无 PCIe 往返 |
| **多相机 / 4 路以上并发** | RK182x（8 路 88.6 FPS）或内置 NPU（8 路 69.7 FPS） | 高路数下 RK182x 领先 1.27 倍、4 路时基本持平；NPU 免费但要占用 SoC |
| 板子还要跑别的模型 | Hailo-8（单路）或 RK182x（多路） | 两者的算力都在模块里，RK3576 的 NPU 可以留给别的任务 |

**RK182x 的价值需要重新界定**：1–2 路它比内置 NPU **慢**（16.2 / 34.4 对 21.2 / 43.2，
PCIe 往返）；4 路基本持平；8 路领先 1.27 倍。它真正不可替代的地方是**算力不在 SoC 上**——
用模块时 RK3576 的 NPU 可以留给别的模型，这在多任务场景下才是决定性的。

**Hailo-8 的价值在单路**：单路把设备跑满（51.2 FPS 设备侧）、延迟最低，而且不占 SoC 的 NPU。

要提高 Hailo 侧的总吞吐，Hailo 的方案是**增加模块**（一模块一路），
而不是在一块模块上堆多路——这与 RK 系列"一块模块内部分核扩展"的思路完全不同。

## 说明

1. 单路数据为同一脚本重复运行中的最后一次；多路每档各测一次。
2. 多路测试不含画框与编码；真跑 8 路并各输出标注视频，主机 CPU 会先成为瓶颈
   （单路已可见：加上画框与写 MP4 后 49.2 降到 28.3 FPS）。
3. 本机无硬解（缺 Rockchip MPP 插件），4K 原片只有 16.5 FPS 上限；真机应使用 VPU 硬解。
4. 这块板的 PCIe 链路是 **Gen2 x1**，而 Hailo-8 模块本身支持 Gen3 x4——
   官方标称的 155 FPS 在此链路下不可达（实测 Hailo 官方 HEF 为 52.5 FPS）。
5. RK 两端的运行时都是每次调用一帧，这是各自 Python 绑定的用法（RKNN3 1.0.4 没有
   `rknn3_run_async`，rknnlite 也未暴露 run/wait 分离接口），因此它们多路数字来自
   "一路一进程、一路一核"的测试。
6. 两支对比视频随结果发布（`results/clips/`：单路、8 路）；逐设备的标注视频不随本交付发布。
   每台设备的第 200 帧截图随结果发布，三张截图的像素级校验记录在
   `results/single_stream/frame200_check.json`。
7. 数据与图表均由脚本从原始 JSON 生成：`common/make_final_figures.py`、
   `common/make_osd_figure.py`；原始记录、字段清单，以及本次交付对记录做过的全部编辑
   （都是描述或命名字段，没有改动任何测量值）见 `results/README.md`。
