# Results: what is here, and where every number comes from

All records in this folder were produced by the six runners in this repository, on one
reComputer RK3576 devkit, with the models in `model/` (hashes checked against the records).
Nothing here is hand-edited except the four field changes listed at the bottom, which are
configuration or naming fields - no measured value was touched.

```
results/
  single_stream/
    <device>/video_result.json          the run: per-frame detections + timing of every layer
    <device>/frame200.png               frame 200 of that run's annotated clip (640x640)
    frame200_check.json                 pixel-level verification of the three screenshots
  multi_stream/
    aggregate_{1,2,4,8}_streams.json    Hailo-8, N streams through one device
    aggregate_8_streams_nodecode.json   Hailo-8, 8 streams, host decode/NMS skipped
    rk3576_multi_stream.json            built-in NPU, 1/2/4/8 streams, one process per stream
    rk3576_multi_stream_1to3_runs.json  built-in NPU, the earlier 1/2/3-stream run
    rk1820_multi_stream.json            RK182x, 1/2/4/8 streams
  derived_video_decode.json             decode cost of the 4K source and its two derivatives
  figures/
    single_stream_bars.png              generated by common/make_final_figures.py
    multi_stream_scaling.png            generated by common/make_final_figures.py
    runtime_osd.png                     the three screenshots side by side (make_osd_figure.py)
    {hailo8,rk3576_npu,rk1820}_frame200.png   copies of the three stills, for convenience
  clips/                                the published comparison videos; they are hosted on the
    compare_1stream_3devices.mp4        SenseCraft CDN and excluded from git by .gitignore
    compare_8stream_3devices.mp4        (64 MB of derived media, regenerable from the records)
```

## Single stream (394 frames of the 640x640 clip shipped as `video/test.mp4`)

The input clip ships with this delivery as `video/test.mp4`. Each record stores the sha256 of
the file it actually read (`input.video_sha256`, identical in all three and equal to that file's
hash), so the records can be checked against the clip they used. The records name it `test_640.mp4`,
which is the file name it had during the runs; the shipped copy is the same bytes.

| Device | Record | inference | + decode/NMS (see note) | + drawing/MP4 |
|---|---|---:|---:|---:|
| Hailo-8 | `single_stream/hailo8/video_result.json` | 51.19 FPS (19.54 ms, device service with 4 inferences in flight) | 49.23 FPS (20.31 ms) | 28.26 FPS |
| RK3576 NPU | `single_stream/rk3576_npu/video_result.json` | 32.93 FPS (30.37 ms, one call) | 23.54 FPS (42.48 ms) | 15.09 FPS |
| RK182x | `single_stream/rk1820/video_result.json` | 22.79 FPS (43.89 ms, one call incl. PCIe) | 17.45 FPS (57.30 ms) | 13.11 FPS |

The "inference" column is the field each runner stores for the accelerator call itself:
`device_service_fps` for Hailo-8 (a throughput measured with the pipeline kept full),
`python_infer_only_fps` for the two Rockchip parts (the per-call time converted to a rate); the
"end-to-end" column is `python_end_to_end_fps` in all three records.

The middle column comes from `pipeline_without_io` in every record, but that field is **not the
same measurement** on the two platforms: the Hailo-8 runner measures the interval between two
finished frames in its no-drawing pass, so it includes the frame read and the letterbox, while the
two Rockchip runners time the RKNN call plus decode and NMS and keep the read and letterbox in a
separate field (`read_letterbox_infer_decode`). Like for like, with the read and letterbox
included, the two Rockchip parts measure 46.11 ms (21.7 FPS) and 62.86 ms (15.9 FPS). The table
above keeps the published `pipeline_without_io` figures, and the intermediate column header in
docs/REPORT.md says what each includes.

## What each screenshot shows

`frame200.png` is frame 200 of that device's annotated clip. The banner in the top-left corner was
drawn by the runner itself, and the two figures on it are fields of that device's own record:

| Screenshot | Banner line 2 | First figure = JSON field | Second figure = JSON field |
|---|---|---|---|
| `single_stream/hailo8/frame200.png` | `FPS 51.2 on device / 49.2 this run` | `timing.device_service_fps` (51.19) | `timing.banner_pipeline_fps` (49.23) |
| `single_stream/rk3576_npu/frame200.png` | `FPS 34.9 infer only / 23.6 this run` | `timing.device_benchmark_total_fps` (34.88, this same client's single-stream rate, printed by the runner; the 394-frame mean of that run is `python_infer_only_fps` = 32.93, which is the figure the tables use) | `timing.banner_pipeline_fps` (23.56) |
| `single_stream/rk1820/frame200.png` | `FPS 22.8 infer only / 16.6 this run` | `timing.python_infer_only_fps` (22.79; this clip was re-rendered from the record after the module was swapped out, so its banner carries that record's own mean) | `timing.banner_pipeline_fps` (16.62) |

`frame200_check.json` is the verification record, produced by `common/check_osd_figure.py`:
for each device the banner is rebuilt from the record, re-rendered with the same font metrics and
compared with the pixels on screen, and it must beat every one-character variant of itself (wrong
digit, wrong device name) - a decoy moves only ~0.1% of the strip, so a plain threshold would
accept almost anything. Each entry also records the banner rectangle measured on the screenshot
(`banner_box_wh_on_screen`), which must match the size the expected two lines need within two
pixels - an extra line of text would make the rectangle taller - and the
OpenCV version used for the check: OpenCV 4.x and 5.x render the Hershey font with different
metrics, so a frame can only be verified under the major version that drew it (the version is in
the record's `environment.opencv`). The same file records that each still matches frame 200 of its
clip (max/mean differences are listed; the clips are lossy) and that `figures/runtime_osd.png` is
exactly the three stills pasted side by side. Text drawn outside the banner rectangle cannot be
detected by this check - the rectangle is exactly the size the runner's two lines need, and the
runners draw nothing else into it.

## Multi stream (aggregate throughput, no drawing or encoding)

| Streams | Hailo-8 (one device) | RK3576 NPU (2 cores) | RK182x (8 cores) |
|---:|---:|---:|---:|
| 1 | 50.34 FPS | 21.20 FPS | 16.18 FPS |
| 2 | 51.26 FPS | 43.24 FPS | 34.42 FPS |
| 4 | 51.62 FPS | 52.28 FPS | 57.04 FPS |
| 8 | 51.60 FPS | 69.65 FPS | 88.58 FPS |
| 8, no host decode | 52.17 FPS | - | - |

Reading the records - the two platforms write slightly different shapes:

- the Hailo-8 files are flat: `aggregate_fps` is the total frames per second across all streams of
  that run, `per_stream_fps` is that figure divided by the stream count, and `per_stream_frames` /
  `per_stream_detections` are per-stream lists. Each stream ran 200 frames through one `InferModel`
  with `depth` 8.
- the Rockchip files are nested under `results[str(n)]`: `aggregate_fps` is the same aggregate
  figure and `per_stream_fps` is a list, one entry per stream. Every stream is its own process,
  RK3576 200 frames/stream and RK182x 300 frames/stream.

`multi_stream/rk3576_multi_stream_1to3_runs.json` holds the earlier 1/2/3-stream run and is kept
because the report's revision note refers to it.

## The two published clips

`clips/compare_1stream_3devices.mp4` and `clips/compare_8stream_3devices.mp4` are the videos built
for publication: the three annotated panels side by side, each panel carrying the device name and
its own live FPS. They are derived media, not measurement evidence - the numbers come from the
JSON records above - and because they are 64 MB of video they are hosted on the SenseCraft CDN and
left out of git (`.gitignore`); the packaged delivery includes them.

## Schema notes

The records were written by the runners as they were at measurement time, so two things differ from
what the runners in this folder write today: the Hailo aggregate records are flat (no `results` key,
see above) and the two Rockchip records come from slightly different revisions of the multi-stream
script (`rk1820_multi_stream.json` entries have no `streams_completed`). The runners here write a
richer record - they add the model and clip sha256, the confidence thresholds and the accepted core
mask per stream - so a fresh run produces the same measurements with more provenance fields, not a
byte-identical file.

Two fields per record are the figures the runner was *told*, not ones it measured in that run:
`hailort_benchmark_streaming_fps` / `_hw_latency_ms` (Hailo-8: 52.53 FPS / 13.89 ms, measured with
Hailo's own `hailortcli benchmark` on this board for this HEF) and `device_benchmark_total_fps` /
`_ms` (RK3576: 34.88 FPS / 28.67 ms, the same client's single-stream rate; RK182x: 29.697 FPS /
33.671 ms from RKNN3's own `rknn3_model_test`). They are printed on the clips' banners and are the
reference behind the tables' device columns; the `rk1820` field is additionally checked above
against that run's own inference mean.

## Edits made to the copied records

Six changes, all listed here; no measured value changed - every timing, per-frame detection,
frame count and file hash is identical to the source record it was copied from (checked field by
field, including all 394 per-frame entries of each run). All text files here use LF line endings,
as the source repository does:

1. `single_stream/*/video_result.json`: `decode.implementation` now names the modules in this
   folder (`common/postprocess_common.py + common/postprocess_yolo26.py`); it previously named the
   module the code used before it was reorganised.
2. `multi_stream/rk3576_multi_stream.json`: `npu_cores` 3 -> **2**. This is a script constant, not
   a measurement: the SoC has two NPU cores, and the runs pinned one stream per core with masks
   `0x1`/`0x2` (4 and 8 streams oversubscribe those two cores, as the report notes).
3. `multi_stream/rk1820_multi_stream.json`: `npu_cores` 8 added (the record did not carry the
   field; the module exposes eight NPU cores).
4. Hailo records (`aggregate_*.json`, `single_stream/hailo8/video_result.json`): the field
   `async_depth` was renamed to `depth`, the name of the runner's command-line option. Same value,
   same meaning.
5. `single_stream/*/video_result.json`: `input.note` said the clip was made from COCO128 images at
   640x480, which was a stale note from an early scratch clip. It now states the clip that was
   actually used - `test_640.mp4`, 640x640, 30 FPS, 394 frames, derived from a 3840x2160 traffic
   clip. The `input.video` / `input.video_sha256` / `frames_processed` fields were already correct
   and are untouched; all three devices ran the identical file (sha256
   `30ec4406e62d37a164c073d44f71d6a7cad70a8eddd26daf5a792a0eba2a2218`).
6. `single_stream/*/video_result.json`: `timing.note` rewritten so it names the field behind each
   figure and states what the middle column includes. The RK3576 note wrongly attributed its device
   figure to `rknn3_model_test`, which is the RK182x tool; the recorded value (34.88 FPS /
   28.67 ms) was measured with the RK3576 runner itself. The two Rockchip notes now also record
   that their `pipeline_without_io` excludes the frame read and letterbox (the Hailo-8 one includes
   both) and that `read_letterbox_infer_decode` holds the full per-frame loop. No value changed.
