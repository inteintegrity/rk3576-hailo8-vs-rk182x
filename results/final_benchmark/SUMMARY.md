# 最终测评：单路 / 多路推理性能（YOLO26n）

测量日期：2026-09-20。模型：`yolo26n`（COCO 80 类，640×640，INT8）。
三端图边界一致（六个 one2one 原始检测头），解码/NMS 由同一份主机实现执行，输入逐字节一致。
RK182x 与 Hailo-8 均使用**各自官方的量化配方/官方编译产物**（Hailo 用官方 HEF）。
测试视频：`video/test.mp4`（3840×2160，394 帧，交通场景）及其派生源。

> **方法说明（2026-09-20 定稿）**：Hailo-8 的两项测试改用 Hailo 官方推荐的**异步管线**
> （`VDevice.create_infer_model` → `configure()` → `run_async()` + `AsyncInferJob.wait()`，
> 深度 4/8 帧在飞），这是 `hailortcli run` 内部的做法，也是 Hailo 文档给出达到峰值吞吐的方式。
> 此前的实现是同步 `InferVStreams.infer()`（提交一批等一批），设备在主机解码期间空转，
> 因此把 52.5 FPS 的设备测成了 33–35 FPS。两套数据都保留：
> 旧口径在 `results/final_benchmark/_syncmethod/`。
> RK3576 与 RK182x 仍用各自的同步绑定（rknnlite / rknn3lite 在 Python 侧**没有**异步接口）。

## 0. 视频源与解码开销

本环境没有可用的硬件解码器（缺 Rockchip MPP 的 GStreamer 插件、无 V4L2 解码节点），
4K 软解成为瓶颈，因此从同一段视频派生轻量源用于加速器对比：

| 源 | 分辨率 | 解码 | 解码上限 |
|---|---|---:|---:|
| test.mp4（原片） | 3840×2160 | 60.7 ms/帧 | 16.5 FPS |
| test_640.mp4 | 640×640 | 2.09 ms/帧 | 478 FPS |
| test_1080.mp4 | 1920×1080 | 9.11 ms/帧 | 110 FPS |

**真机应使用 RK3576 的 VPU 硬解**；这里的软解开销属主机侧限制，与加速器无关。

## 1. 单路推理（394 帧全片：读帧 → letterbox → 推理 → 解码/NMS）

| 加速器 | 配置 | 推理（设备） | 管道（+letterbox/解码/NMS） | 端到端（+画框+写视频） |
|---|---|---:|---:|---:|
| **Hailo-8（官方 HEF，async 深度 4）** | 单设备 | 19.5 ms → **51.2 FPS** | 20.3 ms → **49.2 FPS** | 35.4 ms → 28.3 FPS |
| **RK3576 内置 NPU** | 单模型跑 2 核 | 30.4 ms → 32.9 FPS | 42.5 ms → 23.5 FPS | 66.2 ms → 15.1 FPS |
| **RK182x** | 1 核 | 43.9 ms → 22.8 FPS | 57.3 ms → 17.5 FPS | 76.3 ms → 13.1 FPS |

单路结论：**Hailo-8 领先**（管道 49.2 FPS，是内置 NPU 的 2.1 倍）。
它的设备服务速率 51.2 FPS 已到 Hailo 官方 CLI 实测的 52.5 FPS 的 98%——
也就是说这条链路上，主机侧（letterbox+解码+NMS）不再是瓶颈，设备本身才是。
RK3576 与 RK182x 的数字受各自的同步 Python 绑定限制，不代表其硬件上限。

Hailo 单路的层次分解（同一份 JSON）：设备服务 19.5 ms →
加上读帧/letterbox/解码/NMS 为 20.3 ms（49.2 FPS）→ 再加画框与写 MP4 为 35.4 ms（28.3 FPS）。
**瓶颈从设备转移到了主机的画框与视频编码**（约 15 ms/帧）。

重复运行抖动：仅推理 Hailo-8 三次 34.9–35.7 FPS（旧同步口径）与 51.2–51.8 FPS（异步口径），
内置 NPU 两次 32.9–34.9 FPS。

### Hailo-8 官方标称 vs 实测

| 指标 | 官方 zoo | 本板实测 |
|---|---:|---:|
| yolo26n batch-1 FPS | 155 | **52.5**（`hailortcli benchmark`，Hailo 官方 HEF） |
| 我们自己的异步管线 | — | **51.2**（同一 HEF、同一条链路） |
| 单帧硬件延迟 | — | 13.89 ms |

**原因已定位到平台**：本板 PCIe 链路跑在 **Gen2 x1（5.0 GT/s ×1）**，
而模块本身支持 **Gen3 x4（8.0 GT/s ×4）**——只有其能力的 1/8。
Hailo 官方数字是在链路充裕的主机上测的。我们自己编译的 HEF 是 54.3 FPS，
Hailo 官方 HEF 是 52.5 FPS，**两者一致 → 我们的编译没有问题**；
异步管线达到 51.2 FPS → **我们的主机侧代码也没有问题**。

### 同步口径与异步口径的差别（保留对照）

| 口径 | 单路吞吐 | 说明 |
|---|---:|---|
| 同步提交（旧，`_syncmethod/`） | 管道 26.0 FPS | 一次 `infer()` 一帧/一批，等它返回期间设备空转 |
| **异步深度 4（本次定稿）** | 管道 **49.2 FPS** | 常驻 4 帧在飞，设备与主机重叠 |
| 设备自身（同样异步、无主机解码） | 52.2 FPS | 8 路聚合、`--no-decode`，即设备上限 |

## 2. 多路并发（每路独立解码 + 独立推理，200 帧/路）

| 并发路数 | Hailo-8（async 深度 8） | RK3576 内置 NPU（3 核） | RK182x（8 核） |
|---:|---:|---:|---:|
| 1 路 | 50.3 FPS | 20.9 FPS | 16.2 FPS |
| 2 路 | 51.3 FPS | 42.9 FPS | 34.4 FPS |
| 3 路 | — | 49.4 FPS | — |
| 4 路 | 51.6 FPS | — | 57.0 FPS |
| 8 路 | **51.6 FPS** | — | **88.6 FPS** |

**Hailo-8 的总量仍然是平的**（50.3 → 51.6 FPS，与路数无关），但平的位置从 33 FPS
提高到了 **51.6 FPS——设备自身的上限**（8 路 + 仅设备口径实测 52.2 FPS）。
每路只能分到 1/N（8 路时每路 6.5 FPS）。

- **为什么 Hailo 不能靠加路数提升总量**（实测定位，详见 `logs/hailo8_why_no_multistream.md`）：
  设备不向用户暴露核划分、独占打开（连 Hailo 官方 CLI 开第二个进程都被拒：
  `HAILO_OUT_OF_PHYSICAL_DEVICES`），单帧 13.9 ms 的延迟把整台设备锁在约 72 FPS，
  实测内部流水线跑到 52 FPS 已接近该上限。
- **RK182x 随路数线性增长到 88.6 FPS**（8 核），是 Hailo-8 的 1.7 倍。
- **RK3576 内置 NPU 增长到 3 核封顶**（49.4 FPS），低于 Hailo-8 的 51.6 FPS。

**多路结论（同口径 aggregate throughput）：
RK182x 88.6 FPS > Hailo-8 51.6 FPS > RK3576 NPU 49.4 FPS。**
Hailo-8 的定位是"单路高吞吐/低延迟设备"：**它把 N 路都服务到自己的满速，
但不随 N 增长**；要提高 Hailo 侧总吞吐，Hailo 的方案是**增加模块**，而不是在一块模块上堆多路。

## 3. 结论：各加速器适用场景

| 场景 | 选择 | 理由 |
|---|---|---|
| 单路 / 单相机 | **Hailo-8** | 管道 49.2 FPS（内置 NPU 23.5）；设备延迟 13.9 ms 最低 |
| 单路但不想插模块 | 内置 NPU | 23.5 FPS，免费、无模块、延迟 30 ms |
| **多相机 / 4 路以上并发** | **RK182x** | 8 路聚合 88.6 FPS（Hailo 51.6、NPU 49.4 封顶） |
| 8 路以上再扩展 | Hailo-8 加模块 / RK182x 加模块 | 两者都靠加模块扩展，但 Hailo 一模块只能服务一路满速 |

**RK182x 的价值在并发密度**：一块模块替代 3 个内置核以上的工作量，
代价是每路帧率从 16.2 降到 11.1 FPS（8 路时），且主机要同时喂 8 路。
**Hailo-8 的价值在单路**：设备侧 51.2 FPS、单帧 13.9 ms，且不占 SoC 的 NPU。

## 4. 边界与未完成

1. **多路测试不含画框与编码**（刻意，测推理服务容量）。真跑 8 路并输出 8 路标注视频，主机 CPU 会先成为瓶颈
   （单路已可见：画框+写 MP4 让 49.2 降到 28.3 FPS）。
2. **4K 软解瓶颈**：本环境无硬解，4K 原片只有 16.5 FPS 上限；真机应走 VPU。
3. **Hailo-8 的 PCIe 链路只有 Gen2 x1**，是这块板对它的硬限制，官方 155 FPS 在此不可达。
4. **RK 两端的 Python 绑定没有异步接口**（rknn3lite 的 `rknn3_run_async` 在 1.0.4 上不可用；
   rknnlite 未暴露 rknn_run/rknn_wait 的异步用法），因此它们的数字是**同步口径**，
   与 Hailo 的异步口径不同源；若要严格同口径比较，需要改用 C API，本轮未做。
5. **内置 NPU 超订（4/6/8 路共享 2 核）未测**：多路对比按"每路独占 1 核"进行。
